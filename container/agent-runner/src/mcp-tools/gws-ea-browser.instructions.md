# Host browser mechanics

Use `browser` with one ordered action list. Separate tool calls have no ordering guarantee. A batch stops at its first failure or navigation; inspect its returned observation before continuing. Every element ref belongs to its observation generation. Batch actions use flat ref and generation fields; sign-in and purchase tools use nested target refs. Never invent selectors or reuse refs after a new observation.

The host budget defaults to 90 seconds from acceptance and cannot exceed 100 seconds. Tools wait 120 seconds. A timeout does not cancel accepted work. Keep its request id and use `request_status` before another action; do not repeat a mutating request. Only `list_watches` is safe to repeat. A late screenshot is returned as an image through the same status tool. The action’s image_index identifies its image in the response, starting at zero.

Actions available in `browser` are navigate, observe, screenshot, click, type, select, key, scroll, wait_for, form_input, upload and download. Text and form input accept ordinary text only. The host refuses secret/payment fields, clipboard shortcuts and screenshots while a secret is present. It does not expose JavaScript, field-value reads, cookies or storage. Upload only a regular file from this job’s own session; downloads arrive in its inbox.

Use `fill_secret` with a host-listed item handle, login field, target and submit refs. Never send a password or one-time code as text. Use `sign_in_code` with the target and send refs before requesting the email. Assistant mail is consumed by the host. For a principal mailbox, set from to principal; report awaiting_code and its recorded site to main, which relays the principal’s answer. Start a fresh observation after submitted, code_filled or link_opened. Report missing items, origin mismatches, ambiguity and unavailable vaults to main.

Use `purchase` for every money, hold, deposit, conditional fee, trial or subscription commit. The host reads the checkout and seeks authority. Await the result after awaiting_principal. Unsupported merchant flows or unreadable terms cannot commit. After outcome_unknown, use the reconcile operation with its attempt id and a current page ref; never supply a verdict. confirmed_placed or confirmed_not_placed is host-verified evidence. inconclusive leaves purchases blocked; main handles the principal’s decision. A changed or lapsed checkout needs a fresh observation before continuing.

Use `save_recipe` with a task name, inclusive global job action range and named inputs. Bind a type/select value, a single-field form_input value, or a click target’s exact accessible name, such as a slot label. The trace indices span requests, including navigation stops. Use `run_recipe` with the returned recipe id and ordinary input values. It stops before a commit. completed means all recorded steps finished without a purchase; reached_commit_point supplies the ref for `purchase`; checkpoint_failed supplies the failed step, expected and found state, and page for repair. Repair with `browser`, then save the corrected range.

Use `watch` with its read-only recipe, site, named inputs, venue identity and name, party size, exact time windows, financial bounds and deadline. Currency is an uppercase three-letter code; maximum total is an exact decimal string in major currency units. Financial terms are requested limits; the host verifies merchant terms. Await armed or principal approval, then wait for the host’s report. `list_watches` reads this job’s watches; `cancel_watch` ends one. A commit already in progress finishes and reports before cancellation completes. Calendar conflict or unavailable calendar wakes the job without booking. All watches together can book only once for this job.
